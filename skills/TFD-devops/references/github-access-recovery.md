# Recover GitHub access

1. Confirm the [governed](project-governance.md) host, target, operation and actor. Diagnose from the process that failed. For a user session, check `gh auth status --hostname HOST` and `gh api --hostname HOST user --jq .login` in that runtime. Check which profile or credential source takes precedence without printing values. For an installation token or Actions job, identify the installation or workflow, event and job from its own evidence.
2. Record the failing method, endpoint or job, status and sanitized error. For a network error, check host reachability in that runtime. For 401, verify the sign-in or token lifetime. For 403 or 404, verify target, visibility, policy and endpoint permissions. Use `X-Accepted-GitHub-Permissions` if present. A successful read only proves reading. [REST troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)
3. Give the operator the supported cause or remaining uncertainty, who can act, the exact screen and minimum setting, and the readback to run. Apply only authorized changes. Block only the affected operation.

| Where it failed | Operator action and readback |
| --- | --- |
| Local or agent-managed `gh` | The operator signs into the correct account through that host's supported connection flow. Recheck the effective login and repeat the read probe in the same runtime. [GitHub CLI authentication](https://cli.github.com/manual/gh_auth_status) |
| GitHub App writing repository Issues | The repository owner checks **Settings → Applications → Installed GitHub Apps → Configure** for a personal owner, or **Organization Settings → Third-party Access → GitHub Apps** for an organization. Confirm the exact repository is included and the installation grants **Issues: write**. With an App user token, also verify the user's effective repository access via the same host. Check `GET /user/installations` and `GET /user/installations/{installation_id}/repositories` for the intersection. An installation token uses its own scope and needs no collaborator invite. [Installation settings](https://docs.github.com/en/apps/using-github-apps/reviewing-and-modifying-installed-github-apps) · [App user token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app) · [Create Issue](https://docs.github.com/en/rest/issues/issues#create-an-issue) |
| Confirmed missing collaborator access for an App user token | For a personal repository, the owner checks **Repository Settings → Collaborators**. If the correct account has an expired invitation, the owner replaces it and the invited account accepts it. For an organization, the owner checks the applicable repository role or team. Recheck the account's access and the installation's repository list after acceptance. [Collaborator invitations](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository) |
| GitHub Project | The Project admin checks **Project Settings → Manage access**, the Project owner and actor's role. For an App, compare its registered Project permission with the grant on the Project owner's installation. If the App has not requested it, its maintainer must add it. If approval is pending, the installation owner reviews it. Read back the exact Project ID and the permission needed for the operation separately from repository Issues. [Project access](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects) · [App permission changes](https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration#changing-the-permissions-of-a-github-app) |
| GitHub Actions job | Check **Repository Settings → Actions → General**, inherited policy and runner access. For the automatic `GITHUB_TOKEN`, adjust only the affected job's `permissions` if authorized. Check the trigger and fork restrictions. If the job uses an App token, follow the App checks. Verify a permitted run on the expected commit and event. [Actions token authentication](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication) |

After correction, recheck the same identity, target and operation. Before retrying an authorized write, check for a previous result to avoid duplication. Verify the resulting resource. Use read-only checks when no write is authorized.
