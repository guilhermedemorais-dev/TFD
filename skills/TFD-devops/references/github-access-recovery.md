# Recover GitHub access

1. Confirm the [governed](project-governance.md) host, target, operation and actor. Diagnose from the process that failed. For a user session, check `gh auth status --hostname HOST` and `gh api --hostname HOST user --jq .login` in that runtime. Check which profile or credential source takes precedence without printing values. For an installation token or Actions job, identify the installation or workflow, event and job from its own evidence.
2. Record API, method, endpoint/job, status and sanitized error. Check network reachability in the failing runtime. On 401, check sign-in/token lifetime and, for GraphQL, App query/mutation permissions, including Projects. Insufficient App permissions yield GraphQL 401 or REST 403; status alone cannot identify the cause. On 403/404, check target, visibility, policy and endpoint permissions. In REST, inspect `X-Accepted-GitHub-Permissions` if present. Reads prove only reading. [App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app#choosing-permissions-for-graphql-api-access)
3. Give the operator the supported cause or remaining uncertainty, who can act, the exact screen and minimum setting, and the readback to run. Apply only authorized changes. Block only the affected operation.

| Where it failed | Operator action and readback |
| --- | --- |
| Local or agent-managed `gh` | Reconnect through the host's supported flow only for wrong identity or invalid/expired credentials. With correct login, check permissions; confirmed missing repository access follows below. Repeat the read probe in the same runtime. [CLI authentication](https://cli.github.com/manual/gh_auth_status) |
| GitHub App writing repository Issues | The owner checks **Settings → Applications → Installed GitHub Apps → Configure** (personal) or **Organization Settings → Third-party Access → GitHub Apps** for repository selection and effective **Issues: write**. If unrequested, the App maintainer adds it under **App registration → Permissions & events → Repository permissions** and saves. If pending, the installation owner approves the update; recheck the grant. For App user tokens, also verify user access via `GET /user/installations` and `GET /user/installations/{installation_id}/repositories` in the same host. Installation tokens need no collaborator invite. [Permission changes][app-grants] · [App user token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app) · [Create Issue](https://docs.github.com/en/rest/issues/issues#create-an-issue) |
| Confirmed missing repository access: user credentials or App user token | The owner grants minimum required access through **Repository Settings → Collaborators** (personal) or the organization's repository/team role. Invited users accept; replace invitations only if expired. Recheck the same account's access and, for App user tokens, the installation's repository list. [Collaborator invitations](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository) |
| GitHub Project | The Project admin checks **Project Settings → Manage access**, the Project owner and actor's role. For an App, compare its registered Project permission with the grant on the Project owner's installation. If the App has not requested it, its maintainer must add it. If approval is pending, the installation owner reviews it. Read back the exact Project ID and the permission needed for the operation separately from repository Issues. [Project access](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects) · [Permission changes][app-grants] |
| GitHub Actions job | Check **Repository Settings → Actions → General**, inherited policy and runner access. For the automatic `GITHUB_TOKEN`, adjust only the affected job's `permissions` if authorized. Check the trigger and fork restrictions. If the job uses an App token, follow the App checks. Verify a permitted run on the expected commit and event. [Actions token authentication](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication) |

After correction, recheck the same identity, target and operation. Before retrying an authorized write, check for a previous result to avoid duplication. Verify the resulting resource. Use read-only checks when no write is authorized.

[app-grants]: https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration#changing-the-permissions-of-a-github-app
